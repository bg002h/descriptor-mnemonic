## (e) Witness-item vectors

The labels are correct.
- **Script size.** `chained_multis(n)` is n 20-of-20 `multi` fragments; each script is OP_20 + 20 × 34 + OP_20 + CHECKMULTISIG = 683 bytes. 5 × 683 = 3415, under 3600.
- **Ops.** 21 per `multi` (1 plus 20 keys); 5 × 21 = 105, at most 201.
- **Witness items.** 21 per `multi` (20 signatures plus the dummy); 5 × 21 = 105 > 100, and 4 × 21 = 84.
- **The test asks rust-miniscript directly.** `the_witness_item_limit_alone_refuses_five_chained_multis` runs `Segwitv0::check_local_validity` over 20 real keys. That check runs size, then ops, then witness items, so a "witness items (limit: 100)" error means the earlier checks passed. The same test asserts `policy_type_checks` gives false for 5 and true for 4.
- **The cases.json pins.** `untyped_witness_items_over_100` is pinned `!typed && !complete`. The new `typed_` prefix branch pins `typed_witness_items_84` as typed. The count assertion 30 + 40 + 3 + 33 is consistent with the 106 cases the CHANGELOG states.

## Minor

### m-1. On a keyless card, the gate runs before the "keyless TEMPLATE" check, which changes the exit code and points to a flag that cannot help

**Where:** `crates/md-cli/src/cmd/address.rs:65` (gate) before `:70` (`is_wallet_policy`); `crates/md-cli/src/cmd/descriptor.rs:145` before `:155`.

**Measured:** `md address <untyped keyless card>`, for example `untyped_review_or_b_thresh`.
- Pre-decision: rc 2, "address requires wallet-policy mode … this card is a keyless TEMPLATE".
- HEAD: rc 1, "this card's policy is not valid miniscript … pass --allow-invalid-miniscript".
- Following that advice prints "WARNING: … Funds sent to this wallet may be UNSPENDABLE…" and then the old rc 2 keyless refusal. Nothing is rendered.

**Effect:** this applies to all 59 untyped keyless cases.json cards on both verbs. No funds are at risk. It changes the exit code (2 to 1) of an existing refusal and sends the operator to a flag that only adds a warning before refusing anyway.

**Fix:** move the gate below the `is_wallet_policy` check in both verbs. The decision says "render", and a keyless card is never rendered. A one-line test with an untyped keyless card would pin the order.

### m-2. The toolkit manual and GUI schema mirror for the new flag are still owed

`--allow-invalid-miniscript` is a new md-cli flag on `address` and `descriptor`. The repo rule says the toolkit manual chapter (`42-md.md`) and mnemonic-gui's md schema mirror update in lockstep with the implementing PR. Both are filed as open FOLLOWUPS (`md-address-allow-invalid-miniscript-manual`, `-gui-schema`, `design/FOLLOWUPS.md`, end of the bh1125 block), not done. This is fine on a branch. Before this ships, the paired toolkit PR is needed, or the manual's flag-coverage lint fails.

### m-3. `policy_type_checks` still says addresses never consult it

`crates/md-codec/src/policy_shape.rs:468-469`: "Display and identity only: decode, ids, addresses and re-encoding never consult it."
- It is still true of md-codec's own `derive_address`.
- But `md address` and `md descriptor` now gate on it, and the Go port reads this doc as the rule's contract.
- Suggested addition: "md-cli's `address`/`descriptor` refuse a card that fails it unless `--allow-invalid-miniscript` (Brian, 2026-11-26)."

## Nit

### n-1. The flag help lists fewer rules than the gate enforces

`crates/md-cli/src/main.rs:633-638` and `:831-836` list "(an untyped tree, a tap leaf whose root is not B, or a tap leaf that can never be satisfied)". The gate also refuses timelock-range, placement and script/satisfaction-limit failures. The refusal text itself (`build.rs:62-66`) does say "type, timelock or script-limit rule". Suggest "for example" in the help, or the same list.

### n-2. `CliError::Unsupported`'s doc says that variant never calls the input "invalid"

`crates/md-cli/src/error.rs:79-91` says the `unsupported:` prefix is a statement about md's capability, and that an unsupported shape is "never 'invalid'". The new message (`build.rs:62`) reads "md: unsupported: this card's policy is not valid miniscript". This is the variant Brian named, and the text is accurate. Only the variant's doc comment is now slightly out of step. Widen the doc, or leave it.
